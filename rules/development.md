# 開発ルール

**このファイルには「毎回効く判断ルール」と「踏むと静かに壊れる罠」だけを置く。**

## 基本

- コンテキスト節約のため、調査やデバッグにはサブエージェントを活用する。ただし**通読が必要な品質レビューは委譲しない**（原稿全体の一貫性チェック、自分の設定ファイル群の見直し等）。分割委譲すると章間の繰り返しや直し漏れが視界から外れる。
- 「変更不要」「問題なし」と結論する前に、必ずその根拠を明示する。ドキュメントやソースを確認せずに「正確です」と言わない。
- **全体スコープへの断定**（「このコードベースには〜がない」等）は、`grep -rn` 等で全ファイル横断スキャンしてから言い切る。一部のファイルだけ見て全体を断定しない。
- **1件の指摘は、そのクラス全体の指摘として受け取る。** 「p.228のキャプションが無い」と言われたら、直すのは指摘された1件ではなく同じ条件に当てはまる全箇所。ただし広げるのは「不備の判定条件」であって「直し方の値」ではない。指摘されていない要素は元のまま残す。
- **「◯件ある」と要約する前に、必ず全件を列挙して検算する。** 目視で数えた件数は外れる。列挙できたなら、その検査をスクリプト化して残す。
- 判定一覧を出すときは、各行の根拠の信頼度（実コード確認 / ドキュメント確認 / 主観 / 推測）を明示する。
- パッケージ・ライブラリを選定するときは、選んだ理由と代替案を必ず示す。
- WebFetchでURL本文が取得できない場合（JS描画ページ等）は、推測で進めずユーザーに本文のコピペを依頼する。

## 確認していないことを、確認した形で言わない

**「たぶんこうです」を「こうです」に丸めない。** 断定してよいのは、自分でその一次情報を読んだときだけ。読んでいないなら「未確認」と書くか、先に読んでから答える。

- **件数・分類・状態は、全件を1件ずつ読んでから言う。** 全件読むコストが高いなら「N件中M件を確認した。残りは未確認」と書く。
- **エラーで見られなかった経路は「無かった」に含めない。** 認証切れ・権限不足で開けなかった場所は、開けなかったことを明記する。
- **他人の資料に書いてある事実も、裏取りするまで自分の結論にしない。**

## 大規模出力を親コンテキストに取り込まない（`Prompt is too long` 対策）

`git diff` 生パッチ・大量grep結果・長大ログ等を親のメッセージ履歴に直接流し込まない。

| 出力の目安 | 処理方針 |
|-----------|---------|
| 500行未満 / 数十KB以下 | 親で直接読んでOK |
| それ以上 | サブエージェント（general-purpose）に委譲し、要約・判定結果（表・JSON）だけ受け取る |

- 編集・コミット等の副作用のある操作は親が担当し、子は読み取り・分析に限定する。

## サブエージェント並列起動は原則逐次

親コンテキストが重い状態で複数並列にすると `Prompt is too long` で失敗しやすい。①並列をやめて逐次処理（完走確実性優先）②親のコンテキストを事前に軽くする ③渡すprompt を簡潔にする ④どうしても並列なら2〜3個まで、の優先順で対応する。

## 「調べつくして」系の網羅指示で、無断の大規模ファンアウトをしない

「調べつくして」「徹底的に」「網羅的に」は、**規模の白紙委任ではない**。4体以上のサブエージェント起動や多段オーケストレーションを始める前に、計画の規模を1〜2行で提示して確認を取る。ユーザーが規模を明示したとき（「エージェント10体で」等）だけ確認なしで進めてよい。

## perl / sed 一括置換の `|` エスケープ漏れ事故

`perl -pi -e 's/| foo | bar |/.../'` のように**パターン先頭・中間の `|` を未エスケープ**にすると、正規表現の交替として解釈され**空文字列にもマッチ → 全行の行頭に置換文字列が挿入**される事故になる。

- Markdown テーブル行など `|` を含む置換は `\|` に全てエスケープするか、Edit ツール / Python スクリプトを使う。
- 一括置換後は必ず `head` / `git diff` で対象ファイルの構造を目視確認する。
- 複数ファイルへの機械置換後は「同一行頭が多数行で繰り返される」等の壊れパターンをgrepで検査する。

## 複数作業の混線防止（CWD干渉・ステージ範囲）

- Bashの並列実行間でも working directory は共有される。`cd` を使わず **`git -C <path>`** でリポを明示し、異なるリポの更新を同一メッセージで並列にしない。
- `git add -A` / `git add <dir>/` は**並行セッションの未コミットファイルを巻き込む**。対策の優先順：
  1. 自分が触ったファイルパスを明示列挙してadd する
  2. `git commit <path> -m "..."` でパス指定コミット
  3. コミット前に `git status --short <dir>/` で目視。見覚えのないファイルは別セッションの作業
  4. `git add -A` は「自分しか触っていない」と確信できるときだけ
- ⚠️ **復元に相対リビジョン（`HEAD~1` 等）を使わない。コミットハッシュを明示する。** 自分が最後に見た `HEAD` は並行セッションのコミットで既にずれていることがある。

## 設定ディレクトリをシンボリックリンクにしていると、検索の書き方しだいで静かに空振りする

`~/.claude/` 配下をリポジトリへのシンボリックリンクで管理している場合、**検索コマンドはリンクの扱いが実装ごとに違い、外すとエラーも警告も出さず終了コード1（＝該当なし）で返る**。

- 具体パスを引数に指定して `rg` で引くのが既定。`~/.claude/` を丸ごと再帰するなら `rg -L` が要る。最も確実なのはリンク先の実体（`~/git/claude-code-kit/`）を直接見ること。
- `/usr/bin/grep -r` はリンクの種類によって0件を返すことがある。0件を「無い」の根拠にする前に、必ず存在するはずの語で1回引いて、検索が対象を読んでいることを確かめる。
